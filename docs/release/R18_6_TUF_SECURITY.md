# R18.6 — TUF metadata and anti-rollback/freeze verification

## Scope

R18.6 adds an offline, testable TUF trust layer for release metadata. It is independent from GitHub Release naming and does not publish a release, sign production artifacts or submit anything to WinGet.

The implementation uses maintained Python packages:

- `tuf>=7,<8` for the TUF metadata model and verification semantics;
- `securesystemslib[crypto]>=1.4,<2` for isolated Ed25519 test signing.

Synthetic keys generated by the acceptance suite are fixtures only. They are not production release keys and make no public trust claim.

## Top-level roles

The synthetic repository always contains the four TUF top-level roles required by the R18.6 contract:

- `root.json` — key authority and signature thresholds;
- `targets.json` — authorized target path, length and SHA-256;
- `snapshot.json` — version/hash/length binding for `targets.json`;
- `timestamp.json` — version/hash/length binding for `snapshot.json`.

The verifier persists trusted `root`, `timestamp`, `snapshot`, `targets` metadata plus a compact `state.json`. A later verifier instance restores this state from disk before checking a new repository view.

## Verification order

`TufUpdateVerifier` fails closed and performs the following checks before replacing trusted state:

1. load an explicit bootstrap root or the already persisted root;
2. reject root rollback or non-sequential root updates;
3. verify root threshold against the previously trusted root and the candidate root;
4. verify timestamp, snapshot and targets signatures against the candidate trusted root;
5. evaluate all expirations against the injected deterministic verification clock;
6. reject timestamp, snapshot or targets version rollback against persisted state;
7. require timestamp → snapshot version/hash/length agreement;
8. require snapshot → targets version/hash/length agreement;
9. verify target payload length and SHA-256 against `targets.json`;
10. atomically persist the newly trusted metadata and compact state only after every check passes.

A failed verification never promotes the candidate metadata into trusted state.

## Mandatory acceptance matrix

| Case | Expected |
| --- | --- |
| valid update from trusted state | PASS |
| rollback of `timestamp` | REFUSED |
| rollback of `snapshot` | REFUSED |
| freeze with expired metadata | REFUSED |
| `targets.json` referenced by a wrong digest | REFUSED |
| new `root` without its required signature threshold | REFUSED |
| trusted state restored after verifier restart | PASS |

The focused unit suite also rejects a bad `timestamp` → `snapshot` hash/length reference.

## Deterministic time

Tests use the fixed UTC verification instant `2026-09-05T12:00:00+00:00`. Expiration results therefore do not depend on the wall clock of the CI runner.

## CI evidence

`.github/workflows/r18-6-tuf-acceptance.yml` runs on Ubuntu and Windows, checks out the exact evidence SHA, compiles and lints the focused sources, executes the focused tests and emits `artifacts/r18_6/tuf-acceptance.json`.

The workflow has `contents: read` only and asserts:

- all seven mandatory cases passed;
- trusted-state persistence is enabled;
- no network is required by the synthetic acceptance path;
- no production keys are used;
- no public GitHub Release, production signing or public WinGet submission is triggered.

R18.6 completion still requires the roadmap-mandated broad gates: R0 Repository Guard, full Python Core and this specialized TUF acceptance on the exact END head, followed by exact-head merge and the unique post-merge continuity normalization.
