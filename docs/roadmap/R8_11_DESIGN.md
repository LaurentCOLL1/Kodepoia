# R8.11 — Adversarial hardening + R8 integrated acceptance — Design

## Frozen objective

R8.11 proves that the complete R8.1–R8.10 asset/Vault stack remains safe, deterministic, recoverable and correctly connected to the accepted R3/R4/R5/R6/R7 foundations. It does not introduce a new asset subsystem and it does not authorize R9 implementation.

## Hardening scope

The R8.11 adversarial suite targets cross-boundary failures that isolated subdivision tests may not expose:

- Vault traversal, absolute-path and symlink escape behavior;
- forged/tampered canonical manifests and poisoned rebuildable SQLite indexes;
- content mutation and atomic materialization/promotion behavior;
- transform output escape, cache poisoning, lineage identity and cancellation;
- duplicate/fingerprint evidence without destructive auto-merge;
- semantic-search unavailable/stale/governance-blocked behavior;
- hostile description/license/provenance text remaining data rather than authority;
- Git path and option-shaped filename handling through structured `--` path boundaries;
- malformed/non-canonical/oversized Git LFS pointer evidence;
- license/BOM conflicts and governed export blockers;
- Godot cache/rebuild source preservation through the already accepted R8.9 bridge;
- bounded many-asset fixtures using tiny generated bytes rather than committed heavy binaries.

The suite may strengthen an accepted implementation when it discovers a safety defect, but it must not weaken an existing gate or reinterpret a frozen subdivision contract.

## Transform-cache hardening rule

A valid Vault revision is not sufficient evidence for a valid transform-cache hit. A cache hit must remain bound to the request that produced it. In particular, cached output evidence must not redirect a request for one logical output asset to a different logical asset merely because the input/recipe bytes are otherwise valid.

R8.11 therefore treats cache output identity, expected role/kind and lineage as security/integrity evidence. Poisoned or mismatched cache metadata becomes STALE/CORRUPT and the transform is rerun through the accepted staging/promotion path.

## R8-specific integrated acceptance model

`kodepoia.assets.acceptance` is intentionally separate from the frozen R7 Research acceptance implementation. It defines:

- `R8IntegrationStatus`;
- `R8ManualState` with derived satisfaction semantics;
- `R8SubdivisionEvidence`;
- `R8IntegrationReport`;
- canonical evidence builders and repository validation.

The model requires exactly `R8.1` through `R8.11`, in order. Each subdivision is bound to its canonical `docs/roadmap/R8_<n>_ACCEPTANCE.md` Git blob, exact SHA-256, exact byte length, accepted implementation head, manual state and non-empty manual reason.

Passing integrated evidence cannot contain explicit or derived blockers. The accepted R8.11 implementation head must equal the report `source_sha`.

## Canonical repository evidence

The final verifier will load acceptance documents with `git show HEAD:<path>` rather than trusting the mutable working tree. Git documents `<revision>:<path>` as a way to show the blob contents stored at that revision; blob contents are treated as uninterpreted bytes, making exact byte-length/SHA-256 validation suitable for this acceptance evidence.

`docs/roadmap/R8_INTEGRATED_ACCEPTANCE.json` will be deterministic, schema-versioned and checked in only after the R8.11 implementation head is frozen. The verifier will regenerate the expected report from Git blobs and fail closed if the checked-in JSON differs.

## Manual-state policy

R8.11 manual intervention is `CONDITIONAL` by the frozen plan. The expected final state is `CONDITIONAL NOT TRIGGERED` when:

- R8.5 and R8.8 inherited conditional gates remain resolved as not triggered;
- R8.9's authoritative local Godot gate remains `REQUIRED SATISFIED` with its accepted evidence;
- hosted CI can execute the R8.11 integrated verifier and full regression matrix.

If an inherited environment-specific gate becomes unresolved, only that already-defined gate may be re-run. R8.11 does not create a new broad manual procedure.

## Final acceptance sequence

1. Implement adversarial hardening, R8-specific report contracts/schema and focused tests.
2. Run R0 Repository Guard, full Python Core and KodeStudio UI Smoke; freeze one exact R8.11 implementation head only when all are green.
3. Create `R8_11_ACCEPTANCE.md`, the deterministic generator/verifier and Linux CI hook using the frozen implementation head.
4. Let the verifier print the canonical JSON candidate while `R8_INTEGRATED_ACCEPTANCE.json` is absent.
5. Check in that exact candidate and synchronize continuity.
6. Re-run R0, full Python Core and UI Smoke on the final evidence head. The verifier must now compare the checked-in JSON byte-for-byte with regenerated evidence and report PASS with `blockers=[]`.
7. Merge R8.11 only after those exact-head gates succeed.
8. Perform a post-merge continuity-only normalization recording the R8.11 merge and R8 COMPLETE; do not modify canonical acceptance documents after the integrated report is bound to their blobs unless the report is regenerated and reaccepted.

## Security invariants retained

- no arbitrary model-supplied executable, argv, cwd, environment, host, Git refspec/config key or filesystem escape;
- no destructive duplicate auto-merge;
- no search popularity/source-count promotion into truth;
- no license inference from hostile text;
- no export when governance/reuse blockers remain;
- no missing/invalid evidence converted to READY/PASS;
- no heavy binary fixtures committed for acceptance;
- no R9 implementation until R8 is merged, normalized and declared COMPLETE.

## Manual intervention

**CONDITIONAL.** Expected final resolution: **CONDITIONAL NOT TRIGGERED**, provided all inherited environment-specific gates remain resolved and hosted CI can execute the integrated acceptance path.
